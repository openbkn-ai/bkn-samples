## 已复核的关键事实

### 1. 冻结题集与当前数据不一致，不能直接宣称新版延续 100%

题集/答案集均为 50 条且 ID 集合一致：M 15、F 15、R 9、S 11。历史基线为数据快照 2026-08-13、业务日期 2026-08-25；[2026-08-31 正式报告](../samples/supply_ontology_hand/bkn-eval/reports/2026-08-31/comparison.md)记录 A 50/50，B 26/50。

当前锁定 CSV 与历史金标对照：

| 题目 | 冻结金标 | 当前 CSV 离线聚合 | 差异 |
| --- | --- | --- | --- |
| M-07 未关闭预测数量 | 46840 | 56340 | +9500 |
| M-08 未关闭预测张数 | 87 | 90 | +3 |
| M-12 U00-000080 未关闭预测 | 9 张 / 10500 | 12 张 / 20000 | +3 张 / +9500 |
| M-10 382-000005 销售汇总 | 签约 1081 / 发货 1066 / 差额 15 | 40 张订单，1081 / 1066 / 15 | 数值一致，能力缺失 |

新增 ID 为 `0000023181-FUTURE`、`0000023181-SHORT`、`0000023181-CONTENTION`，数量分别为 3000、6000、500，业务日期均为 2026-08-15。指标资产及查询例已写 90/56340，答案集仍写 87/46840。仅将函数的业务日期设为 2026-08-25，不会自动把新增预测排除在聚合之外。

Git 历史追溯：这三行在提交 [`b163a709`](https://github.com/openbkn-ai/bkn-samples/commit/b163a709f4e0626b4b3f8bc531f9d8415133c17a)中一同新增，提交时间为北京时间 2026-08-15 10:41:12；随 [PR #2](https://github.com/openbkn-ai/bkn-samples/pull/2)于北京时间 2026-08-15 23:26:13 合并。提交同时新增未来预测用例测试。因此“新增”指相对 2026-08-13 冻结快照的新增，不是本轮优化或近期部署新增；它们在 8 月底历史评测之前就已进入仓库。历史评测使用的线上数据库是否包含这三行，须凭当时的安装/数据证据核对，不能仅从报告日期推断。

建议保留两条独立、可核验的基线：

1. 历史回归：恢复并核验原始冻结快照的全部表摘要，在隔离安装中运行原 50 题与原金标，目标 50/50。若只按日期过滤，需要证明所有题目都遵循统一的时点可见性；不能为三道题临时加过滤来凑分。
2. 当前版本验收：使用新版 sample 实际交付的数据，由独立评测流程重新核验受影响金标，保存新的题集/答案集身份、数据摘要与报告。仍保留 50 道核心业务问题，目标 50/50，但须明确该结果属于新基线。

不要覆盖历史报告或在同一答案集版本中静默把 87 改为 90。数据影响需要覆盖全部预测、MRP、争用及交期路径，本次只确认了以上三个主数据差异，未给其余 47 题作在线通过判定。

### 2. #27 是取数失败，纯计算通过不足以证明部署正确

`tools/mapping/column_types.yaml` 明确声明 `erp_mds_forecast.id` 为 `VARCHAR(64)`。issue 评论进一步提供了真实对象查询的原值命中、去零值不命中证据。

本次用当前 CSV 的字符串 ID 模拟对象 API，并经真实 `load_bkn_rows` 入口复现：首个条件为 `id == "23181"`，随后出现 10 次无过滤 BOM 分页查询，最终报超过 5000 行。直接将完整 CSV 交给纯计算适配器，F-14 则返回 57 节点。两条结果表明必须同时测试 loader、生成的发布函数和在线调用。

现有 `test_native_function_bkn_contract.py` 固定去零条件；`test_native_function_bundle.py` 将数字 ID 转为整数，掩盖字符串资源下的问题。修复时须覆盖字符串、数字兼容、含字母 ID、未知 ID，以及原值/规范值发生碰撞时的明确处理，避免合并不同业务记录。

F-14 的正确目标仍为 `report_grain=full_tree`、`node_count_total=57`。未知预测单的验收不是“没有 5000 行报错”而是“明确未找到，且未查询 BOM/库存/采购”。

### 3. #28 之外还有 5 组指标名称不一致

| 答案集名称 | 实际资产名称 | 题目 |
| --- | --- | --- |
| 产品数量 | 产品总数 | M-01 |
| 物料数量 | 物料总数 | M-02、M-13、M-14 |
| 供应商数量 | 供应商总数 | M-03、M-15 |
| 销售订单数量 | 销售订单数 | M-04、M-09 |
| 仓库数量 | 仓库数 | M-05 |
| 签约数量合计 / 发货数量合计 | 无对应资产 | M-10 |

前五组属于概念名/发布名差异，须明确映射或更新版本化 basis；M-10 是实际缺少能力，不能按别名处理。现有 `test_eval_source_of_truth.py` 检查 50 个 ID、函数与 Skill 覆盖，未检查指标引用完整性、数据聚合与金标一致性。

建议补齐两个销售订单 sum 指标，绑定销售订单对象，按 `product_code` 服务端过滤，并提供 382-000005 → 1081/1066 的真实查询例。C 可以接受业务等价的可回放对象聚合路径；不可因为没调用不存在的指标，直接把正确答案判错。答案判分、资产一致性和依据诊断应分别报告。

### 4. #63 要验证口径，不能只保留天数断言

当前规则：外购/委外取 `purchase_fixedleadtime`，其他属性取 `product_fixedleadtime`。本次离线适配器对 606-000989 返回 14 天，对 528-000036 和 382-000005 返回 1 天，均未返回口径。

[#63 的后续 G6 评论](https://github.com/openbkn-ai/bkn-samples/issues/63)指出自制交期仍缺口径。修改说明虽然是正文允许的方案，但不能自动满足该 G6 的自制/生产来源验收。优先扩展兼容返回，并另验正式对象 ID 与数据来源；`loaded_datasets=["material"]` 是内部数据集别名，不应作为 `ot_id`。

扩展验收须让采购/生产字段取不同值，覆盖外购、自制、委外和缺失属性。缺失属性的现有默认规则须明确说明或版本化调整，不能输出未经主数据支持的采购/生产结论。

### 5. #23 不宜给所有指标随意添加时间字段

产品/物料/供应商规模、仓库去重、实时库存属于全量或快照；单张当前库存记录的日期不自动代表历史库存。趋势需要真实时间语义和数据覆盖，同环比需要本期、比较期，普通分组占比需要分组、分母与过滤口径。

按四种模式建立逐指标能力矩阵与预期值：

- 快照即时：不隐式附加时间范围；明确指定期间时按能力提示或校验。
- 趋势/同环比：只对具有有效对象属性映射及日期覆盖的时间指标开放；固定历史窗口或相对策略，避免 2026-10-12 的默认最近 24 小时查历史数据为空。
- 普通占比：即时分组聚合，明确分母；按时间占比另行配置时间语义。
- 未关闭条件：必须验收过滤后的业务值，137 条全量返回不能充当未关闭数；当前数据对应 90，历史基线对应 87。

前端通用能力修复属于 Studio；sample 负责资产、数据、查询例和业务口径，遵循开发指南“不要增加样例专属的 Studio/安装服务代码”。`power_layer.py` 同名跳过创建，因此改 JSON 后重跑 create 不证明旧定义已更新。正式新版遵循卸载/重装边界，不能宣称支持原地升级。

## 新版验收门禁

| 门禁 | 必须满足 | 证据 |
| --- | --- | --- |
| G0 版本与数据一致 | 平台主线 SHA/镜像、sample 新版本、包摘要、数据镜像 digest、全部表摘要、题集/金标身份、业务日期均固定 | 版本清单、安装结果、数据核验；历史与当前基线分开 |
| G1 资产完整 | 对象/关系绑定正确；函数与 Skill 可发现；所有 basis 指标有实际定义或明确版本化映射；逻辑属性有效 | 实际能力目录、注册/绑定结果、真实对象/指标查询 |
| G2 核心准确率 | A 完整 50/50；分组 M 15/15、F 15/15、R 9/9、S 11/11；未运行/失败题留在分母中 | 逐题原始答案、判分、关键数字/集合/日期/澄清结论 |
| G3 issue 扩展验收 | #27 ID 与早停；#28 两指标过滤汇总；#63 属性/来源契约；#23 四模式、无时间范围、切换残留、条件过滤 | 扩展用例全部通过，单独统计，不混入原 50 题凑准确率 |
| G4 证据与治理 | 每题 Interaction 可回放、正式能力被调用；无金标泄漏、无 CSV/SQL 降级替代线上 A；只读、不写回 | Interaction ID、tool/metric ID、输入、关键输出、起止时间及结果 |
| G5 产品安装与发布 | 干净离线安装和正式远程安装均验证变化；版本说明如实披露兼容性 | 固定包验收、目录刷新、实际版本、真实业务查询 |

核心必须保留的高风险断言：F-14 57 节点；M-10 1081/1066/15；F-04 534；F-05 3850=3800+50；F-06 35 条缺口；F-10 唯一缺料 321-000569、净缺 240；S-07 成品 534 覆盖 50、余 484；S-08 2026-09-29、晚 19 天；S-09 3850 满足；S-10 3851 不满足、差 1。仓库范围、BOM 去重、替代料、在途和争用次序不得为修复体验而改变。

正式评测按 [体验评测指南](../samples/supply_ontology_hand/bkn-eval/体验评测指南.md)隔离执行：A/B 只能读题集；A 只走线上 BKN；B 只读同一数据库快照，不能读源码/金标/历史报告；答案冻结后 C 才读金标。研发已读答案集的当前会话及本次离线复算不作为盲测 A。若做 A/B 对比，须另外完整重跑 B，不能拿旧 B 报告对比新 A。

历史 100% 是答案一致性成绩；历史报告同时披露 Skill 编排足迹和完整平台 Trace 不足。新版必须分列答案准确率、扩展契约通过率及证据完整性，不能以答案满分自动关闭契约或审计缺口。

## 建议实施顺序

1. 从最新主线建实施分支；固定 8081 的实际平台版本与隔离验收方式，先解决 G0 的历史/当前数据基线。
2. 修 #27 取数与早停，修 #63 返回契约，补 #28 指标/绑定/查询例；每项同时补针对真实缺陷的测试，避免继续固化错误假设。
3. 在 sample 包内完成 #23 的指标能力矩阵、时间指标及查询验收；平台前端问题只记录外部依赖，不纳入 sample 修改。新增演示数据若影响核心统计，先更新独立基线。
4. 真实安装候选包，先运行受影响题，再完整运行 50 题和 issue 扩展验收，保留新批次原始结果与 C 判分。
5. 只有 G0–G5 满足，才将该版本标记为“50/50、100% 且 issue 验收通过”，随后按开发指南发布新版本。当前 sample 范围的候选修改已实现；#23 的平台前端问题属于外部依赖；#23 真实四模式回归、干净安装及正式 50 题评测待完成，见 [实施记录](supply-sample-implementation-status.zh-CN.md)。
