## 实例与依赖

用户指定验收地址为 `http://localhost:8081/`。只读检查确认：根路径 302 跳转到 `/studio/`，Studio 页面返回 200；`/api/studio/samples` 返回 nginx 404。这说明样例接口在该路径尚不可用，不能据此判断平台本身不支持样例，需要核对安装服务是否部署及网关路由。

初次检查本机 `openbkn --version` 返回 0.1.5，`openbkn auth status` 返回未配置 token。随后按用户要求启动浏览器登录，CLI 的平台版本检查报告实际版本为 `0.2.0-main.20261009001912.sha628dd24`，因基础版本不匹配退出，未保存会话。SDK 比较去除预发布元数据后的 MAJOR.MINOR.PATCH，因此需先准备固定提交的 SDK 0.2.0，再登录和确认身份。

用户另提供本地 MCP AppKey 文件；密钥仅在内存用于指定实例的只读权限请求，没有写入代码或日志。该请求返回 HTTP 502，身份和权限尚未确认，不能归因为密钥无效。平台导入和数据库变更未执行。

后续结果：已从安装镜像使用的 SDK 提交 `703921dbd2affd39c07c65f65e05b4ae0f266187` 在工作区构建 CLI 0.2.0，由用户完成浏览器授权，登录为 admin。使用该会话读取 permissions（scope=type）确认 is_admin=true，Catalog 列表及 backend health 可用，health 再次返回上述平台版本；读取 `supply_ontology_hand` 返回 404，当前未发现该网络。MCP AppKey 单独读取知识网络返回 401，后续核对使用已授权会话；该结果不判断它在其他 MCP 通道上的有效性。

只读核对与候选构建均未执行样例脚本、创建资源或运行场景测试。全局 CLI 仍为 0.1.5，验收使用工作区隔离的 0.2.0；依赖安装使用锁文件，未自动更新 SDK 依赖或运行测试。

## 内容与安装链路

候选保持原始 KN JSON、11 个对象到表的绑定、1 个仅加载表 `customer_entity`，以及 14 个函数、3 个技能。数据库共 12 张业务表；JSON 共 15 个对象类型。

| 对象范围 | 当前映射 | 验收要求 |
| --- | --- | --- |
| material、product、bom、inventory、supplier、forecast、mrp、pr、po、mps、salesorder | 对应 11 张业务表 | 逐一确认目标资源绑定、主键及对象查询 |
| mon_task | 映射明确 bind:false | 确认它不依赖业务表绑定，相关能力不伪报就绪 |
| pr_decision、mon_item、skills | 未列入对象到表映射 | 查明用途及创建／能力依赖；不能仅因未列入而视为验收成功 |
| customer_entity | load_only_tables | 验证数据加载及实际关联用途，不补造对象映射 |

平台 hook 按现有顺序执行：导入 KN JSON → 创建／扫描 Catalog → 绑定资源 → 注册原生函数 → 发布技能。JSON 通过 `/api/ontology-manager/v1/knowledge-networks` 导入，不交给原生 BKN tar loader；函数依赖 Foundry 的 `sandbox_sdk`、`@tool` 和对象查询能力。原生 BKN 路径留作协议已声明的后续接入，不混入此次供应链 JSON 验收。

导入脚本会在工作副本添加归属标签，遇到 index_config 不兼容时重试剥离旧字段。必须记录实际是否发生剥离并确认模型语义；源归档固定且不改写。已有同名但非安装器管理的资源应拒绝复用。

## 验收顺序与结果记录

1. **连接与身份**：确认实例、管理员、平台版本、默认模型、Catalog/KN/Function/Skill 所需接口；认证失败时不推进写操作。
2. **制品与环境**：从固定提交重新构建候选，固定安装服务、SDK、数据库和平台镜像摘要；确认网络连通与持久卷。不得把仓库源码目录的运行结果作为候选包验收结果。
3. **数据库**：在隔离样例库准备数据；核对 12 张表及约定行数、加载顺序和关联命中率。拒绝覆盖人工业务库。
4. **模型与绑定**：导入并读取网络，核对 15 个对象、内部引用及 11 个业务绑定，解释非业务对象；逐对象执行查询，记录目标资源 ID 与环境映射。
5. **能力**：确认 FUNCTION_CATALOG 声明的全部 14 个函数启用、3 个技能发布；至少调用需求满足、替代料、倒排等代表场景，并记录输入、实际结果、数据来源和业务预期。是否要求逐函数调用由覆盖实际功能的验收用例确定，不能只凭启用状态声明全部可调用。
6. **实例与 Studio**：部署样例服务及路由；确认目录刷新、说明语言回退、指定版本确认、成功版本记录、失败后重试和已安装入口。Pod 重建后再次核对状态和入口。
7. **发布**：汇总固定摘要的结果，填入真实兼容范围与验收证明，通过发布 PR 后生成 stable 目录；尚未支持的远程执行链路继续返回不可安装。

现有 verify_platform.py 的 `capability-callable` 是兼容旧接口的检查名。本地已收紧为“所有声明函数都启用”，仍不是函数调用证明。表发现／对象查询／跨表查询也由聚合 smoke 结果给出；完整验收必须保留 smoke_report 的细项，不能只保存三个布尔值。

验收记录至少包括：候选摘要、依赖摘要、实际平台版本、架构、起止时间、操作者身份标识、各阶段结果、资源 ID、模型变换及场景结果。凭据不写入候选、证明或日志。失败候选不进入正式目录，成功记录必须对应同一份包字节。

在下述实际安装验收之前，本计划尚未执行模型校验、安装脚本或场景测试；已完成入口、认证、平台版本和只读前提核对，以及代码梳理。后续需核对测试实例部署、数据库执行入口和候选所需 Python 依赖；当时持久化部署、样例服务路由和远程制品执行仍需实施。

部署盘点已确认本地 kind-bkn-dev 有默认 standard 存储类，平台位于 openbkn，未部署样例服务。已在本地补 PVC、Recreate、原子写入与构建上下文排除规则，并生成候选部署清单；镜像及源码仍含未提交改动，不能作为正式验收的固定提交证据。迁移和限制见 [状态持久化](sample-state-persistence.md)。

候选服务镜像已按用户 M5 环境构建 linux/arm64。查询官方 SWR／GHCR 的数据镜像 0.1.0 时，未返回可用摘要，不能确认该制品可安装；当前查询函数没有保留具体 HTTP 错误，因此不能断言是未发布、权限还是网络问题。数据执行器已在本地改为无可用摘要时于 apply 前失败，使用解析后的 digest 引用，并限制镜像切换为相同摘要。这只固定一次部署选择，不代表重试已持久锁定原数据库摘要，也不证明镜像通过平台验收；后续仍需补齐固定候选数据制品与真实执行验证。

## 2026-10-09 实际安装与验收结果

本轮发现并修复：

1. 原始网络 3 个描述标签加 3 个归属标签超过后端最多 5 个标签。工作副本保留全部归属及前两个描述标签，导入报告列出省略的 `生态伙伴`；源 JSON 不改写。
2. SDK 0.2.0 Catalog get 经过 JSON envelope 解析后是数组。现支持单条数组／entries／对象，并拒绝空、多条及 ID 不匹配。
3. hook 非零退出且 code 为空时，结构化失败原因被通用错误覆盖。现保留明确 ok:false 的失败信息。
4. 函数和技能发布后未挂载到网络。安装 hook 现定向挂载实际 14 个函数 ID 与 3 个技能 ID，就绪检查同时核对启用／发布状态与网络绑定。
5. 本地平台已有 MinIO，但无默认 OSS Gateway 存储。按现有部署初始化方式创建 `bkn-oss` 桶并注册默认存储，连接检查 200；此配置属于平台前提，不放入 sample 执行脚本。凭据未写入报告。
