# 金融行业专家视角模拟评审：FIBO 双语交易后控制样例

评审身份：资产管理、证券交易后运营、估值控制和金融数据本体专家视角模拟，不代表真人行业资质或外部机构背书。

评审范围：`/private/tmp/bkn-samples-fibo/samples/financial-fibo-{en-us,zh-cn}`，包括 PRD、本体规范、FIBO 映射、20 张 CSV、100 题与金标准、BKN 对象定义及验证器。结论限定于批准的投资组合交易后控制场景，不以完整金融业或全量 FIBO 为验收范围。记录针对本轮优化前的固定样例，后续行号可能因修复变化。

## 总体判断

业务链条基本成立，20 张表的对象选择适当，没有理由为了 FIBO 库规模机械扩张实体类型。合成实体标识、股票/债券报价因子、按交易日/结算日分别计量、价格缺陷阻断整组合分母、严格区分未结算卖出应收与监管交易对手风险、权重平均成本和实际/计划视图，都做了明确限定。双语事实结构一致，数值答案可复现。

但当前不宜直接宣称“严谨完整的验收样例”：存在交易与结算日历不合理、三月计划结算假设缺失、验证器允许未来知识/币种污染、事件 SQL 与事件增量语义不匹配、安装后本体字段业务定义不足，以及复杂题答案解释缺失。应修复以下项并重新生成全部派生量与双语金标准。

## P1：必须优化

### 1. 实际证券交易/结算/报价使用周末，失败状态早于到期日

- `data/securities_transactions.csv`：200 笔 2026-11-22（周日）实际成交。
- `data/settlement_events.csv`：200 笔 2027-01-24（周日）实际结算；`SE-029-2-4`（行 575）2027-02-22 即标记 failed，但指令 2027-02-24 才到期；同类 18 条。
- `data/market_prices.csv`：196 条周末日期价格被当作当日市场价。
- 影响：金融运营用户容易误认为 T+2 是日历天，或结算失败无需到期；陈旧价边界也失去实际意义。
- 最小修复：显式声明虚构的周一至周五、无地区节假日、示例 T+2 工作日规则，不冒充 CNY/USD/EUR 市场通用真实规则。月末快照保留月末日期，价格采用前一工作日；失败/部分结算日期放在到期日或之后。增设日历、事件不早于到期的验收控制。月末 FX 可以是虚构估值日转换率，但需写清不是周末交易价。

### 2. 三月全部预测交易都不结算，没有可解释的计划结算假设

- `data/settlement_events.csv:18` `SE-001-1-5`：2027-03-22，pending，0，forecast_only，planned；全部 200 条三月事件均如此。
- `data/counterparty_exposures.csv:6` `CE-001-5`：正常组合 PF-001 的三月应收为 768.38 USD，当前为 0；大量正常组合都在远超过正常结算日的月末出现未结算应收。
- 影响：计划视图变成“未来交易默认永不结算”，对未来应收/限额的比较产生系统性偏差；planned 标识能避免冒充实际，但不能代替结算预测假设。
- 最小修复：为三月设置清楚的正常预期结算、部分/失败例外、前期未结算恢复分支，记录均保持 planned 且 known_date 不超过观察日。字段定义说明计划行中的状态代表预期状态。至少选择一笔历史 pending/partial 在三月恢复，展示全生命周期，而非新增框架。

### 3. 独立验证器存在可复现的未来知识、状态和币种盲区

对内存 CSV 深复制，每次只修改一字段，执行 `verify_data(data, contract)`，以下五例均错误通过：

| 表/记录 | 注入变更 | 本应拒绝的原因 |
|---|---|---|
| trade_orders / ORD-001-1-4 | known_date=2099-01-01 | 当前实际成交不可能依赖未来才知道的订单 |
| fx_rates / FX-CNY-2027-02-28 | published_date=2099-01-01 | 估值使用尚未发布汇率 |
| positions / POS-001-1-4 | currency=EUR | 对应工具和开仓均为 CNY，成本与已实现损益币种被错误标注 |
| counterparty_exposures / CE-001-4 | known_date=2099-01-01 | 当前风险结论含未来知识 |
| settlement_events / SE-001-1-4 | view_kind=planned | 实际持仓计算仍消费计划结算量 |

- 位置：`tools/verify.py:69–91`（订单/交易）、`110–112`（结算事件）、`120–153`（FX/估值）、`176–190`（应收）。相关模板 `tools/financial_fibo/assets/verify.py` 同需修复。
- 最小修复：对所有带 view_kind/known_date 的表统一执行观察日控制；实际持仓不可使用 planned 事件；核对开仓、持仓、交易、指令、工具的本币一致性；FX 发布日期和 known_date 不晚于可用时点；issuer_exposures/limit_assessments 同样需检查。把上述反例加入负向测试。

### 4. 事件 SQL 隐含“一笔交易只有一条事件”，与已声明的增量事件语义冲突

- `docs/bkn-modeling-spec.md` 定义每条 settled_quantity 是增量而非累计。
- `bkn-eval/questions.json:356` FIN-020 直接 join 所有 settlement_events 后计算 COUNT、gross_amount 及 `trade_quantity-e.settled_quantity`。
- 同类 FIN-024、025、027、028、029、030、050、085、088。当前只有一事件/指令，因此冻结答案恰好正确，不能证明事件模型正确。
- 反例：一笔 100 单位卖单先 pending=0 后 settled=100，FIN-020 会计成 2 笔、合约金额翻倍，并遗留 100 单位应收；FIN-024 仍把旧 pending 行判逾期。
- 最小修复：以业务 as-of 和 knowledge cut-off 过滤事件，按指令累计 settled_quantity、独立取得最新有效状态；再连接到交易，确保每笔交易一行。计划与实际事件隔离。新增一条恢复链即可暴露错误，无需新表。验证器累计事件时按日期排序，并限定所属视图可用性。

### 5. BKN 语义在安装后不够自足

- `kn/object_types/positions.bkn:29–37` 全部 Description 只是复述 Display Name，尤其 `realized_pnl` 未说明“当月、本币”；`cost_amount` 未说明剩余成本；`unsettled_delta` 未说明有符号差值。
- `counterparty_exposures.bkn` 未在字段层说明只算卖出、非净额、非 EAD；`issuer_exposures` 缺少分子/分母和缺价阻断定义；`fx_rates` 缺方向和 USD/源币单位定义；全部对象概要都用同一通用句。
- 外部规范有较好的定义，但消费者通常首先读安装的本体，不能假设总会查到仓库文档。
- 最小修复：20 个对象补一段各自业务定义；所有关键度量、日期、状态、币种、外键补精确双语描述，明确单位、公式、时点和空值含义。保留现有表和关系数量，避免额外实体或函数。

### 6. “完整答案”中的解释实际上 100/100 逐字重复题目

- `bkn-eval/expected-results.json` 英文、中文均全部 `explanation == questions.question`；`evidence_rule` 也是完全相同通用句。
- rows 是正确的机器金标准，但对于“为什么阻断”“解释报价转换”“区别失败与超限”等题，重述问题不构成业务解释或评分标准。
- FIN-070 加权平均成本、FIN-067 不完整组合、FIN-087 失败≠超限、FIN-095/099 新限额预测尤其需要推导与结论。
- 最小修复：每题添加短业务结论及该题必要口径，复杂题包含公式/分母/日期及不应作出的推论；数值仍以 rows 为准。不要把逐行复制的大型数据表写成冗长叙述。

### 7. PRD P0-5 的“从违规到交易及结算原因”缺乏完整综合验收

- `docs/PRD.md` P0-5 要求将违规追溯到持仓和交易，存在结算例外时显示。
- FIN-080 当前只到 assessment→exposure→valuation→position→instrument，未到交易；FIN-085 独立查询卖单，FIN-088 单独重算应收，未形成统一的限额→贡献交易→结算状态证据链。
- 最小修复：将 FIN-080 或另一道 hard 题升级为发行方违规到相关交易/结算证据；将应收 hard 题给出每笔未结算交易贡献额、累计转移和到期/失败状态并对上限额结果。组合贡献应标识开仓存量与新增交易，不能宣称全部敞口由当月交易“导致”。维持 100 题及 30/40/30 比例。

## P2：适度改善，不应扩张业务范围

1. 一些 hard 题主要是查表计数或简单两表汇总（如 FIN-018/019），复杂性偏低。可优先用上述事件恢复、跨期知识控制和完整违规证据链替换，保留覆盖面，勿机械增加问题数。
2. 严格 `>` 阈值规则已经写明，但没有恰好等于阈值的边界测试；补阈值相等及差一最小计量单位的负/正例即可，勿增加新的风控模型。
3. 150 条 FX 仅 15 条被 valuation FK 直接使用；其余为日期汇率曲线，若保留应注明其用于交易/结算调查的价值并选一题使用，而不要仅为记录数填充。无需增加 FX 表数。
4. FIN-009 的 NULL 角色比较采用 `issuer_role<>'issuer'`，在 issuer 缺失时 SQL 三值逻辑不会算错角色；当前有完整外键验证，所以不是当前错误答案，但审计题最好显式 `IS NULL OR ...`。

## 不应要求补齐、目前不算缺失的范围

不要求全 FIBO 导入闭包、衍生品、抵押品、监管资本、正式 NAV、会计总账、AML、投资建议、真实 LEI/ISIN、生产行情源或价格审批系统。这些在 PRD 已合理排除。50 个组合、100 个工具、两类资产和三种币种足够支撑声明场景。可以继续保留六个精确 FIBO 锚点与明确本地扩展，不能把 20 个运营对象宣称为全 FIBO 转换。

不需要为了通过本轮 review 增加指标、函数、Skill。当前固定快照+关系+只读 SQL 能表达业务需求，重点是纠正语义和验收可信度。

## 建议复验

1. 日历规则、三月计划结算、累计事件和所有派生量重建。
2. 双语 key、字段、数值、SQL 结构及业务定义等价校验。
3. 全部 100 题重放与逐题结论核对，不能只比较生成器重建的同源答案。
4. 上述 5 个 FALSE PASS、报价单位/因子错配、未来已知限额、重复事件/恢复事件、阈值边界负向注入。
5. 原生 BKN validate；清楚声明尚未进行平台导入或独立智能体问答验收。
