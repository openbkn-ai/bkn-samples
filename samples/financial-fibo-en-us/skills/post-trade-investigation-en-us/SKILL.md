description: Read-only, evidence-led post-trade exception investigation.
---

Investigate settlement breaks, position valuation, issuer concentration, unsettled SELL receivables, month-end reconciliation and mandate-version exceptions.

1. Establish the actual portfolio IDs, business date, knowledge cutoff and actual/planned view. Clarify essential missing scope. Discover published source properties and allowed values before querying. A DEMO identifier prefix is not an identifier scheme; do not invent properties such as `investment_manager` or `trade_status`.
2. Discover `settlement_asof`, `valuation_asof`, `limit_assessment_asof` and the two recorded-snapshot metrics with `search_capabilities` in the current network. Use actual returned capability IDs. Choose only the function needed: settlement for transfers; valuation for quantities, cost and valuation; limit assessment for mandate decisions. Recorded-snapshot questions require recorded objects/metrics; never silently substitute reconstruction.
3. Fix a bounded portfolio set and small observation-date batch. Each `run_code` invokes exactly one native function through the SDK `execute_tool` helper with its discovered ID. Do not combine several broad native calls in one `run_code`. If comparisons need several functions, make separate calls, retain compact projections, then compare their results. Use optional bounded `additional_observations` only within the published contract; do not assume the candidate limits prove platform feasibility.
4. Validate the tool exit code, error state and non-null result before interpreting rows. Check `completeness`, `issues`, evidence and selection status separately for every returned observation. An ordinary execution failure is not an empty business answer. Pagination or source incompleteness cannot become zero risk or within-limit.
5. In memory, project requested fields, a relevant summary and supporting IDs before printing compact output. Do not print an entire result merely because it fits the candidate 3 MiB compact UTF-8 JSON guard. Never silently truncate required rows or evidence: narrow the next request scope if the complete requested answer cannot fit. Keep every observation's scope and relevant diagnostics. Query atomic records only for requested source facts or source-quality investigation; never access CSV fixtures, evaluation questions, expected answers or gold and never rewrite all financial formulas.
6. Compare recorded metrics with reconstruction only at identical portfolio/entity/business-date/knowledge-cutoff/view grain. Report recorded and reconstructed values distinctly, including reliable values and cache differences. A recorded issuer snapshot can be empty under its global quality policy while a reconstructed issuer numerator is known. Never sum concentration ratios across dates.
7. Preserve independently known fields in blocked rows. Missing opening is unknown, not zero. Unknown valuation elsewhere can block the portfolio denominator and ratios while another issuer amount remains known. Unresolved eligible trade attribution blocks the affected issuer, or all issuer amounts when the issuer cannot be located. A proved zero amount stays zero; zero denominator still leaves ratio unknown. Intraday cost ambiguity does not erase known quantities or qualified market value. `fx_basis=currency_identity` or `zero_amount` with null `fx_id` does not imply a missing required quote.
8. For month-end checks, keep trade-month, local-currency and actual/planned cohorts separate at the requested knowledge cutoff. Distinguish signed booked gross (BUY positive, SELL negative) from remaining SELL notional; do not carry earlier cohorts forward or assume local currency is USD. Use returned facts and evidence, not a parallel financial engine.
9. Explain results in English with date-only dates, explicit units/currencies, money to 2dp, ratios/FX to 6dp and unknowns clearly marked. Native `side` and `status_code` remain stable machine codes; do not translate them. When querying a localized source, use its actual allowed raw enum values. Distinguish partial settlement, overdue and failed; threshold breach and invalid limit selection are separate findings.

Generic request shape: required `portfolio_ids`, `as_of_date`, `knowledge_date`, `view_kind`; optional `additional_observations` is an array of JSON object strings, each containing exactly `as_of_date`, `knowledge_date`, `view_kind`, sharing those portfolio IDs. SDK callers may also pass the equivalent objects directly; do not wrap the complete list in one string. Read the [capability contract](../../docs/business-capability-contract.md) for bounds and envelope shapes. Examples and workflows must not embed question IDs, precomputed answers or gold values.

Read-only investigation: no orders, source writes or notifications; no official NAV, regulatory risk calculation or investment-advice claim.

Multi-observation requests allow at most 20 portfolios and 12 observations including the base; scalar requests retain the 200-portfolio input bound. The guard measures the complete compact JSON serialization as UTF-8 bytes and rejects results above 3 MiB. Native platform preflight observed a 4 MiB result quota; the 3 MiB application guard leaves transport headroom. These input-count bounds do not guarantee that every maximum-size input succeeds: result size depends on records and evidence. On a limit failure reduce portfolios or observations; never truncate required rows or evidence. Acceptance results are recorded separately in the source repository. Input bounds are not universal runtime guarantees. The four specified post-fix tool paths passed separately; this revision remains unpublished.

Query rules: use nonreserved Cypher parameter names such as `$start_date` and `$end_date`; do not use an unescaped `$end`. Stay within the published Cypher subset. If property-to-property comparison is unsupported, retrieve the bounded relevant fields and compare the returned facts in memory, preserving all required rows; use the mounted functions for financial reconstruction. Never interpret query rejection as zero or silently retry the same unsupported query.

Judge the business outcome by `execution_status`. Record `evidence_status` separately: `assembling` is pending, not failure. Follow the documented interaction status API to a terminal evidence state with a bounded timeout; report trace degradation or pending evidence without changing a correct business value.
