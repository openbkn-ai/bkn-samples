# Energy demand-response business contract, version 0.1.0

This is the frozen calculation contract shared by the bilingual sample, implementation and independent evaluator. Source SAREF4ENER supplies semantic concepts, not the following commercial formulas or a certified dispatch algorithm. All data are synthetic. No real dispatch, device control or payment is executed.

## Business scope and stakeholders

A demand-response aggregator must decide what reduction can safely be offered, allocate scarce resources to announced events, and explain delivered response and settlement. Site energy managers need service/maintenance constraints respected; operations need traceable plan-versus-execution exceptions; finance needs threshold, compensation and ledger reconciliation. Use customer-side load reduction (HVAC, refrigeration and EV charging), not generation, battery SOC optimization, power-flow simulation or statutory settlement. Each device has exactly one nonoverlapping meter. Site meters are not added to device meters.

Business dates are YYYY-MM-DD only. A named response block peak_a/peak_b lasts2/3hours, not an all-day window or an hour timestamp. Events with the same date/block overlap completely; different blocks do not overlap. As-of2027-02-28 is the default, with historical facts from November2026 and announced plans/forecasts through2027-03-31. Time-of-day control and intra-block ramps are deliberately outside scope; never infer hourly/instant power safety from block averages.

## Source visibility, versions and missing facts

All functions require event_ids(array1..20), as_of_date and knowledge_date. Valid YYYY-MM-DD dates, knowledge_date may differ from as_of_date for restatement; announced_date<=as_of_date and known_date<=knowledge_date must hold for events. Other source known_date<=knowledge_date. Readiness and planning use the target response_date even when future. Settlement only uses response_date<=as_of_date; future plans return not_due with null financial outcomes. Source records after the cutoff never leak into an earlier view.

Versions: forecast/baseline/readings use logical(device-or-meter,response_date,block_code); offers use(event_id,device_id); execution uses allocation_id. Select maximum revision among visible records, require no two visible records of that revision with conflicting business payload (IDs/known_date ignored). Same-payload retries count once. A tie conflict is an explicit issue, never arbitrarily resolved by primary-key ordering. Status/quality of the latest record is authoritative; do not fall back to an earlier good revision. Malformed scopes fail before source reads. Missing required numerical facts produce null affected outputs, status unknown/completeness partial and evidence IDs; unknown is not zero. Missing offer or expired/withdrawn offer is no eligible resource, not an invented offer.

Numbers are Decimal, never binary floats. kW is average reduction power, kWh= kW*block_hours, rates are CNY/kWh. Quantities/ratios emitted as six-decimal strings, money as two-decimal strings, round half up. Aggregate unrounded Decimal values before final rounding. Unknown ratios remain null; zero denominator is null. IDs/codes remain stable English, business names/status/quality/reason displays are localized.

## Function1 flexibility_assessment

For each visible active offer, require active device, current forecast quality valid, baseline quality approved, nonnegative numeric values, valid_from<=eventdate<=valid_to. Devices of unavailable status, explicitly blocked/opted-out/maintenance constraints, or expired/withdrawn offers contribute known0 with explicit exclusion reason; no data is needed to prove a resource already explicitly blocked. Constraints are known, date-effective, block-matching; type block sets0 and type cap takes minimum cap_kw. Missing cap value is unknown. Eligible device kW=min(offered_kw,device.max_reduction_kw,max(0,min(forecast_kw,baseline_kw)-device.min_service_kw),active caps). Contract does not assume stored forecast equals an approved measurement baseline. Site contribution is min(sum(device eligible),sites.response_cap_kw); event total is sum(site contributions), unknown if any potentially eligible device lacks required sources. Keep rows per event and device_rows with reasons and evidence. Missing required forecast/baseline, visible version conflict or invalid numerics must not silently contribute0.

## Function2 dispatch_plan

Return a deterministic read-only proposal, not a globally optimal power-system dispatch or guaranteed profit. Build the full visible active event pool sharing any requested date/block BEFORE filtering returned events, so asking for a subset cannot obtain the same physical capacity twice. Events ordered priority ascending,event_id; devices cost_cny_kwh ascending,site_id,device_id. Existing visible status committed allocations across the whole block are immutable reservations; proposed/cancelled rows do not reserve. Active-event reservations consume shared device.max_reduction_kw and site.response_cap_kw once, including reservations of unrequested events. Own commitments reduce that event's remaining target. An over-reserved device/site, negative commitment, duplicate allocation for same(event,device), or a commitment outside current eligible device limits emits an issue and leaves affected plan unknown rather than clamping/fabricating a plan. Current eligibility excludes unsafe new allocations.

For a new allocation cap=min(event eligible device kW minus own committed kW, residual shared device physical cap, residual shared site cap, residual event target). Decrement both residual budgets after assignment; never borrow across date/block. Existing committed kW counts even if it is not cheapest now; only new allocation is cost-ordered. Report each event's target_kw,committed_kw,new_kw,total_kw,shortfall_kw,estimated_cost_cny and allocation_rows (existing/new distinguished). Unknown potentially eligible capacity makes the affected block plan partial with null totals; it is not a proof of infeasibility. Not all numeric shortfalls imply permanent physical inability (only present sources/contract).

## Function3 settlement_assessment

Read posted commitments; do not turn a generated proposal into an executed command. Execution latest status completed only is attributable; failed/declined or missing receipt is an explicit unresolved issue. Missing receipt/quality/measurement on a nonzero commitment makes its event's total unknown; explicit failed/declined receipt contributes known0 delivery with an exception. Planned/proposed/cancelled allocations never establish actual delivery. Canceled events return canceled with null outcomes. A past active event with zero commitments has zero delivery, null ratio and zero revenue/cost; target shortage remains a business exception.

For each meter/date/block, require one approved latest baseline and valid latest reading whose duration matches the event block. Meter actual_kwh must be nonnegative. Observed reduction=max(0,baseline_kw*hours-actual_kwh), not absolute consumption or forecast difference. Resolve ALL visible completed commitments across active same-block events before projecting requested IDs. Shared measured reduction is attributed pro-rata by committed_kwh: verified contribution=min(observed_reduction,total completed committed_kwh)*own committed_kwh/total completed committed_kwh. Thus total verified energy never exceeds measured reduction, and each event never exceeds its commitment. A missing shared reading/approved baseline propagates unknown to every affected event; no double credit for the same device meter. Failed receipt allocations have0 verified contribution, are not counted in the attribution denominator, but remain in their event's total commitment for delivery_ratio.

Event committed_kwh=sum(all visible committed allocation kW*hours). verified_kwh=sum(attributed energy). delivery_ratio=verified_kwh/committed_kwh when denominator>0. revenue=verified_kwh*event.reward_cny_kwh IF delivery_ratio>=minimum_ratio inclusive, else0. Customer cost=sum(attributed energy*the latest eligible offer's cost_cny_kwh) regardless whether the aggregator reaches the market threshold; missing offer price makes cost/net unknown. revenue and cost separately round to cents; net=revenue-rounded-cost-rounded. Reconcile latest posted settlement by posted_date<=asof and known<=knowledge: report recorded_revenue_cny and revenue_difference_cny; no posted ledger -> null comparison, not zero. This is the synthetic commercial rule, not a claim of a jurisdiction's electricity-market settlement policy.

## Minimal reusable capabilities and snapshots

Exactly3functions above,2atomic source-snapshot metrics and1read-only investigation Skill per language. Snapshot metrics capacity_snapshots.eligible_kw and settlement_snapshots.delivery_ratio are recorded values for their asof/knowledge pair, not real-time calculations or substitutes for recomputation. Skill routes assessment/planning/settlement, compares cached versus recomputed results, explains evidence/missing facts and avoids actual control/payment. All Skill references are physically inside its references/ directory and included in its attachment manifest. No one-function-per-question design.

## Ten acceptance scenarios and bank mapping

S01 asset ownership, meter uniqueness, units and eligibility; S02 latest load forecast and March planning visibility; S03 offer/maintenance/service constraints and unknown capacity; S04 site limits and no parent/child-meter double count; S05 shared device/site commitments and competing event priorities; S06 deterministic incremental cost ranking and nonoptimality boundary; S07 execution receipts and measured kW-to-kWh performance; S08 late reading/baseline revisions, conflicts and historical knowledge cutoff; S09 threshold-inclusive payment, customer costs and posted-ledger reconciliation; S10 future plan versus actual settlement, snapshot differences and evidence-based exception investigation.

Each scenario has10questions, exactly3easy/basic,4medium,3hard/complex: totals30/40/30 per language. Every question has scenario, requirement ID, business question, explicit date/scope, execution method, expected structured answer, units/tolerance, source evidence and answer rationale. Hard questions combine constraints or dates, do not merely repeat an ID substitution. Independent evaluator derives expected values without importing the implementation; implementation parity alone is not independent correctness. One complete local verification plus fixes of demonstrated failures only; no automatic multiple model rounds. No model-accuracy percentage may be inferred from deterministic checks.

## Frozen code vocabulary and result API clarification

Device status_code active|inactive; event active|cancelled; offer active|withdrawn; forecast quality_code valid|invalid; baseline approved|invalid; reading valid|invalid; constraints block|cap; allocations committed|proposed|cancelled; executions completed|failed|declined; ledger posted|pending. Snapshot quality valid|invalid. Display labels are localized, never used as condition keys. An event pool contains only active visible events; cancelled requested events still receive a cancelled result. Baselines/forecasts/readings can have absent rows or same-revision conflicts in explicitly listed anomaly fixtures.

Posted settlement ledger has no revision: among visible status posted rows with posted_date<=as_of_date select latest posted_date; conflicting payloads on that date yield unknown reconciliation with explicit issue, without invalidating otherwise known physical delivery/revenue. Missing ledger leaves comparison null. Settlement uses approved baseline and actual reading; forecast is not required for actual settlement. Complete-block unknown planning is intentional: potentially eligible unknown sources prevent a confident fully allocated shared-budget proposal.

Common output: scope,rows,issues[{code,source_ids,event_ids}],evidence{table:[source IDs]},completeness(complete|partial),units; plus device_rows for assessment / allocation_rows for planning. All requested visible IDs have a result row; invisible/missing IDs have an explicit event_unavailable issue. Assessment rows event_id,status_code,eligible_kw,target_kw,shortfall_kw; assessment device_rows event_id,device_id,site_id,eligible_kw,reason_codes. Dispatch rows event_id,status_code,target_kw,committed_kw,new_kw,total_kw,shortfall_kw,estimated_cost_cny; allocation_rows event_id,device_id,site_id,kind(existing|new),allocated_kw,cost_cny_kwh. Settlement rows event_id,status_code,committed_kwh,verified_kwh,delivery_ratio,revenue_cny,cost_cny,net_cny,recorded_revenue_cny,revenue_difference_cny. Additional evidence details allowed; no hidden numeric clipping to force a complete result.

Settlement offer pricing clarification: 'latest eligible offer' means latest visible offer whose status is active and validity covers the response date, with a nonnegative cost price. It does NOT require a forecast or current readiness/maintenance eligibility: actual completed delivery cannot lose its compensation solely because an unrelated prediction is missing. A missing/invalid price can make cost/net unknown while retaining known delivery/revenue. Issue code names are implementation details; acceptance checks the business condition, affected IDs and values rather than requiring one spelling.

Unavailable-event output clarification: every requested ID, including a nonexistent or not-yet-announced ID, retains one result row with that event_id, status_code=unavailable and null numeric outputs, plus event_unavailable issue. No invisible event attributes or numeric zeros are invented. A source-known committed_kw remains known on an unknown block plan; only unsafe newly planned totals/cost are null. Device/site ownership remains present for explicitly excluded offers.


## Evidence and explanation contract (0.1.2 clarification)

An unknown site or device capacity keeps an event total unknown, but does not stop collecting other relevant site evidence and issues. Source citation must cover the evaluated scope even on unknown branches. Keep each call's evidence intact; label primary and reference knowledge views separately instead of silently borrowing later evidence.

Explain issues using their affected event_ids and source_ids: distinguish the requested event from other events in the overlapping pool. Explain the business cause and consequence, consulting source offers/commitments/receipts when needed. A withdrawn offer can invalidate an existing commitment without erasing its known committed amount; proposed totals and costs remain unknown rather than safe or zero.

For cross-stage investigations state readiness, planning, measured delivery and settlement completeness separately. Complete settlement cannot certify a partial plan or a complete end-to-end chain. State which stage blocks which conclusion, and identify affected IDs. Keep signed snapshot differences explicit. Interaction finish/trace health is a separate platform outcome, never inferred from business completeness.
