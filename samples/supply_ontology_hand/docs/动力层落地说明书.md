## 2. 一条命令做完（推荐）

```bash
cd tools
python3 power_layer.py all --kn-id supply_ontology_hand
```

等价于依次：

```bash
python3 power_layer.py create --kn-id supply_ontology_hand
python3 power_layer.py bind --kn-id supply_ontology_hand
python3 power_layer.py verify --kn-id supply_ontology_hand
```

有 `config.yaml` 时把 `--kn-id` 换成 `--config config.yaml`。

`create` 按名称幂等：已存在的指标不会再建。`bind` 按逻辑属性名覆盖，其它逻辑属性保留。

## 3. 也可用 CLI 手工做

### 3.1 创建指标

```bash
openbkn --json bkn metric create supply_ontology_hand \
  --body-file ../docs/payloads/metrics-create.json
openbkn --json bkn metric list supply_ontology_hand
```

创建回执只有平台 id。必须再 `list`，用 **名称** 对上 id 和 `scope_ref`。

| 名称 | 必须挂到的对象类 |
|------|------------------|
| 产品总数 | `supply_ontology_hand_product` |
| 物料总数 | `supply_ontology_hand_material` |
| 供应商总数 | `supply_ontology_hand_supplier` |
| 销售订单数 | `supply_ontology_hand_salesorder` |
| 仓库数、库存可用量 | `supply_ontology_hand_inventory`（逻辑属性名 `warehouse_count` / `available_qty_sum`，不可与数据属性重名） |
| 预测需求量合计、未关闭预测单数 | `supply_ontology_hand_forecast` |

平台约束：**逻辑属性引用的指标 `scope_ref` 必须等于该对象类 id**，不能把库存指标挂到产品对象上。

### 3.2 挂逻辑属性

不要手改对象 JSON 里的 metric id。用脚本按名称解析：

```bash
python3 power_layer.py bind --kn-id supply_ontology_hand
```

绑定规格：`docs/payloads/logic-properties.json`。

验收：`openbkn --json bkn object-type get supply_ontology_hand supply_ontology_hand_product` 中应出现 `logic_properties[].name = product_total_count`，且 `data_source.type = metric`、`data_source.name = 产品总数`。

### 3.3 查询验收

可运行 query 体在 `docs/payloads/metrics-query-examples.json` 的 `cases[].body`。先 `list` 得到 metric id，再：

```bash
openbkn --json bkn metric query supply_ontology_hand <metric-id> \
  --body '{"condition":{"field":"materialattr","operation":"==","value":"外购"}}'
```

返回形态：`datas[0].values[0]`。

| 有多少种成品 | 产品总数 | **30** |

| 供应商 / 杨强云 | 供应商总数 | **230** / **51** |

## 5. 伙伴必须知道的平台行为

| 现象 | 做法 |
|------|------|
| 指标定义里的 `condition` 创建后为 null（「未关闭预测单数」不带过滤会得到 134） | 查询时再传 `closestatus_title != 已关闭` 或 `== 正常` |
| `analysis_dimensions` 大约只回 **20** 组，全量按物料分组会丢料 | 定点用 `condition`（料号 / 仓 `and`），不要靠分组结果里找料 |
| 仓预设不会自动生效 | query 里把 `production_available` / `finished_goods` 展开为 `warehouse in [...]` |
| 组合条件 | 本环境 `and` + `sub_conditions` 可用；若目标环境报不支持，分次查询再交并声明 |
| 逻辑属性 `/properties` 算值可能因无 `time_dimension` 失败 | **发现**走对象逻辑属性；**数值**走 `metric query` |
| 对象 `index_available=false` / `doc_count=0` | 不代表没灌数；指标查的是已绑定 resource |
| 创建回执无名称 | 先 `metric list` 再绑定、再 query |

## 6. Agent 怎么用

```text
search_schema / get_object_types
  → 看对象 logic_properties（data_source.type=metric）或 related_metrics
  → 类级规模、过滤、多维：query_metric / openbkn bkn metric query
  → 已挂逻辑属性的实例派生：get_logic_properties_values（若算值失败，回退 metric query）
  → 不要用 run_sql 重算已建模指标
```

仓范围：缺省生产可用 7 仓；问可发货用 3 个成品仓；问全仓则不限制。回答时回显所用仓名单。

## 7. 函数工具箱

指标 P0（8 条）**不用改**。可售、齐套、BOM 结构和物料影响范围不是指标，由独立原生 Function Tool 提供：

| 项 | 当前约定 |
|----|---------------|
| 工具箱名称 | `供应链原生计算函数` |
| 对外工具 | 具名业务函数（BOM 清单、物料反查产品、合计可售、生产计划齐套倒排等） |
| 参数发现 | Agent 先 `tools/list`，再按对应函数的独立参数调用 |
| 执行位置 | OpenBKN Function Runtime；不配置函数服务地址 |

在 `tools/` 注册或更新。脚本按工具箱名称查找，已存在时更新同一工具；不要把返回的 ID 写入 Skill、Agent 或样例契约：

```bash
cd tools
python3 register_native_function_toolbox.py --apply
```

命令返回 `box_id` 和 `tool_id` 后，检查当前环境的发布状态：

```bash
openbkn --json toolbox list --keyword "供应链原生计算函数" --limit 100
openbkn --json tool list --toolbox <上一步返回的-box-id> --all
```

使用方式：第三方 Agent 先通过 OpenBKN MCP 的 `tools/list` 发现函数，再只传入业务参数。函数在 OpenBKN Function Runtime 内通过官方 `sandbox_sdk.bkn` 自行读取所需知识网络对象并完成计算；Agent 不传数据快照、凭据、MCP 地址或函数服务地址。发布前必须用真实 MCP Interaction 验证 Function Sandbox 到 Context Loader 的受管读取链路。业务口径见 [能力口径清单](./能力口径清单.md) §2，Agent 操作说明见 [第三方 Agent 数据交接说明](./第三方Agent数据交接说明.md)。

历史工具箱以及历史统一函数如仍出现在列表中，应保持 `disabled`，不得重新启用或作为体验路径。`tools/fn`、`fn_cli.py` 只用于离线金标和回归验证。

三个数必须分开：理论可产 ≠ 合计可售 ≠ 齐套净需求。替代组 MAX。在途只进净需求/争用。`fn_cli.py` 仅作离线调试。

## 8. 注册技能

源包在 `skills/`：

| 场景 | 目录 |
|------|------|
| S1 齐套倒排 | `skills/production-schedule-backward-planning/` |
| S2 可售能力 | `skills/demand-fulfillment-capacity-analysis/` |
| S3 新需求覆盖 | `skills/demand-fulfillment-requirement-coverage-analysis/` |

```bash
openbkn skill register ../skills/production-schedule-backward-planning
openbkn skill register ../skills/demand-fulfillment-capacity-analysis
openbkn skill register ../skills/demand-fulfillment-requirement-coverage-analysis
openbkn skill set-status <skill-id> published
```

注册后用名称确认三包都已发布；Skill ID 和版本由每个环境生成，不要复制其他环境的值：

```bash
openbkn --json skill list --limit 100
```

预期存在且状态为 `published`：`production-schedule-backward-planning`、`demand-fulfillment-capacity-analysis`、`demand-fulfillment-requirement-coverage-analysis`。当前 Context Loader 的对象类召回仍对 `supply_ontology_hand_product` 返回 `ObjectTypeNotFound`，属于召回索引问题，不影响按 Skill ID 读取或 Toolbox Tool 直接调用。

Action 的说明见 [Action 目录](./catalog/actions.md)：样例仅声明业务意图，未绑定实际 Tool；`tools/actions/` 的回执为本地 `dry-run` 演示，不会写入客户业务系统。
